# MiniStudio 24～36 个月课程路线

> 制定日期：2026-09-03
> 默认投入：每周 8～10 小时
> 当前状态：第 1～17 课及第一个月 v0.1.0 收尾已完成并合并；等待开始第 18 课
> 目标方向：客户端渲染、图形引擎、素材引擎与 AI 创作工具

## 1. 路线定位

这条路线针对的长期岗位同时要求四类能力：

1. 使用 C++ 设计高性能、可扩展的客户端渲染模块；
2. 处理图片、动画、视频和 3D 素材的解析、加载、组合、编辑与预览；
3. 在不同设备、操作系统和 GPU 上进行兼容性与 CPU/GPU/内存/I/O 优化；
4. 设计 AI 生成素材与客户端渲染系统之间的数据协议、Tool Calling 和运行时协作链路。

课程分为两条时间线：

- **前 24 个月是核心路线**：目标是形成可展示的完整作品、达到同方向初级岗位或引擎向技术美术岗位的竞争水平，并开始积累真实项目经验。
- **第 25～36 个月是专家能力进阶**：目标是增加移动端、多媒体、第二现代图形后端、复杂性能问题和架构演进证据。

完成 36 个月课程不自动等于“专家职级”。目标岗位要求的多年商业项目、跨团队协作、线上故障处理和架构责任，必须通过工作、实习、开源协作或真实用户项目积累。

## 2. 学习和课程组织方式

- 每周安排 2～4 个核心课程，每课控制在 20～90 分钟；课程数量随难度变化，不固定为四课。
- 每周剩余时间用于独立编码、调试、阅读、复盘和文档，周总投入按 8～10 小时估算。
- 每个核心课程使用一个独立 Git 分支；同一课的提问、纠错和验收不另开分支。
- 每次只推进一个核心任务。远期路线不代表可以提前批量实现后续模块。
- 每 13 周进行一次阶段复盘，根据掌握质量、可投入时间和岗位变化调整后续内容。
- 每个阶段都必须留下运行结果、错误定位记录、性能数据或设计说明，不能只以“看过教程”验收。

### 架构与代码增长限制

- 从第 9 课起，每次增加功能前先检查目录结构、模块职责、资源所有权和依赖方向；新能力不能默认继续堆进 `main.cpp`。
- `main.cpp` 逐步收敛为对象组装、启动、顶层运行和退出码处理。窗口、Renderer、Shader、Buffer、Texture、场景和资源加载分别形成内聚模块。
- 有状态或拥有资源的职责优先由对象封装，并用 RAII 表达生命周期；无状态算法继续使用普通函数，不为了“面向对象”制造空壳类。
- 每个类只承担一个主要职责，公开最小接口，明确复制/移动规则；模块依赖保持单向，禁止循环依赖、可变全局状态、万能 Manager 和深层继承。
- 优先使用组合。只有出现真实的第二种实现或测试替身时才引入接口与运行时多态；在两个图形后端实际运行前不设计通用 `RenderDevice`。
- 当新代码会让现有文件承担第二个无关职责时，先做最小拆分。每四课和每个版本节点复盘一次目录、依赖和资源所有权，重构前后都必须保持可构建、可运行。

建议的时间分配：

| 类型 | 比例 | 说明 |
| --- | ---: | --- |
| MiniStudio 实现 | 55% | 编码、集成、重构和测试 |
| C++/图形原理 | 20% | 与当前模块直接相关的理论和小实验 |
| 调试与性能分析 | 15% | Debugger、Sanitizer、Profiler 和故障注入 |
| 文档与表达 | 10% | README、架构图、性能报告和口头讲解 |

## 3. 技术路线选择

### 图形 API

1. 先使用 OpenGL 4.1 Core Profile 建立完整渲染直觉；在第一套渲染器完成前不并行学习其他 API。
2. 完成桌面渲染器后进入 Android，使用 OpenGL ES 建立移动端生命周期、设备兼容和性能经验。
3. 以 Vulkan 作为主要现代显式 API，迁移一个已经稳定的核心场景。
4. 只有在至少两个后端真实运行后，才提取 `RenderDevice` 或类似抽象。
5. Metal 放入 25～36 个月进阶阶段，用于验证 Apple 平台与跨后端设计；DirectX 暂缓，除非目标岗位转向 Windows。

### 素材与编辑能力

- 3D 主格式使用 glTF；FBX 先通过成熟库或离线转换处理，不在早期自行实现解析器。
- 先完成图片和 3D 模型，再加入骨骼动画、粒子、2D 动画和视频。
- 编辑器以 ImGui 为起点，重点是素材导入、参数编辑、预览和错误反馈，不追求完整商业编辑器 UI。

### AI 创作链路

- 先学稳定的数据协议、状态机、异步任务、重试、取消、缓存和幂等，再接入真实模型服务。
- Tool Calling 以客户端确实能执行的渲染工具为中心，例如导入素材、创建材质、调整参数和生成预览。
- LangChain、LangGraph、LangSmith、Langfuse 等框架按项目需要选择，不进行无目标的框架巡礼。
- 模型训练、NeRF、3DGS 和可微渲染属于后续专项，不挤占客户端渲染主线。

## 5. 前 24 个月核心路线

### 阶段 A：基础渲染与现代 C++（第 1～3 月 / 第 1～13 周）

核心内容：

- C++ 生命周期、RAII、所有权、移动语义、STL 容器、错误处理；
- CMake、Git、LLDB、编译警告、AddressSanitizer/UndefinedBehaviorSanitizer；
- GLFW、OpenGL 4.1 Core Context、事件循环和 Retina viewport；
- 应用/窗口/渲染职责拆分，以及 Shader、VAO/VBO/EBO、纹理、坐标变换、相机和帧时间。

阶段成果：

- MiniStudio v0.1～v0.2；
- 能从空工程创建窗口并绘制可交互的纹理场景；
- 能解释一帧中 CPU 数据如何变为 GPU draw call；
- 能定位一次生命周期错误和一次 Shader/状态错误。

### 阶段 B：模型、材质与离屏渲染（第 4～6 月 / 第 14～26 周）

核心内容：

- 图片与 glTF 模型加载、Mesh/Material/Texture 的职责和所有权；
- 法线、光照、阴影、PBR 基础、HDR、Tone Mapping 和后处理；
- Framebuffer、渲染目标、多 Pass 渲染和颜色空间；
- `vector`、`unordered_map`、`optional`、`variant`、模板和单元测试在渲染模块中的使用。

阶段成果：

- MiniStudio v0.3～v0.4；
- 加载一个外部模型，正确显示材质、光照、阴影和后处理；
- 提交第一版架构图、资源生命周期说明和 2～3 分钟演示视频。

### 阶段 C：场景、资源与热更新（第 7～9 月 / 第 27～39 周）

核心内容：

- 场景层级、Transform 传播、组件边界和可序列化场景；
- 资源 Handle、缓存、引用关系、失败占位资源和自动释放；
- Shader、纹理和材质热重载；
- `shared_ptr`/`weak_ptr` 的适用边界、类型安全 Handle、接口设计和依赖管理。

阶段成果：

- MiniStudio v0.5；
- 同一资源不会重复加载，删除场景对象不会泄漏资源；
- 修改 Shader 或纹理后可以安全更新，失败时保留可用状态并显示错误。

### 阶段 D：异步加载、动画与编辑器（第 10～12 月 / 第 40～52 周）

核心内容：

- `thread`、`mutex`、`condition_variable`、`future`、任务队列和停止令牌；
- 在正确同步版本稳定后学习 `atomic` 基础、顺序一致性和 acquire/release，不提前手写无锁结构；
- 后台文件读取/解码/解析，主线程 GPU 上传，任务取消与退出清理；
- 2D Sprite、glTF 骨骼动画和粒子系统的基础实现；
- ImGui 场景树、资源浏览、材质参数和实时预览。

阶段成果：

- MiniStudio v0.6～v0.7；
- 大素材加载期间界面保持响应，取消与退出不会泄漏或竞态；
- 形成第一版可公开作品集，并开始用真实 JD 做模拟面试和缺口审计。

### 阶段 E：性能测量与稳定性（第 13～15 月 / 第 53～65 周）

核心内容：

- 帧时间分解、CPU sampling、GPU capture、内存峰值和 I/O 吞吐；
- draw call、状态切换、资源上传、过度绘制和同步等待；
- 基准场景、压力测试、回归数据和错误预算；
- 基础数据结构与算法复杂度在资源查找、排序、剔除和任务调度中的实际影响。

阶段成果：

- MiniStudio v0.8；
- 完成至少两次有复现步骤和数字对比的优化；
- 产出性能报告，说明瓶颈假设、测量方法、修改和副作用。

### 阶段 F：Android 与 OpenGL ES（第 16～18 月 / 第 66～78 周）

核心内容：

- Android NDK、应用生命周期、Surface、输入和前后台切换；
- OpenGL ES 与桌面 OpenGL 的能力差异；
- 屏幕密度、旋转、上下文丢失、设备能力查询和降级策略；
- 真机上的帧率、内存、温度、功耗与 GPU/驱动兼容问题。

阶段成果：

- MiniStudio Mobile Preview；
- 同一个精简场景在 macOS 与至少一台 Android 真机运行；
- 保存设备矩阵、兼容性问题和一次移动端性能优化记录。

### 阶段 G：Vulkan 与跨后端抽象（第 19～21 月 / 第 79～91 周）

核心内容：

- Instance/Device/Queue、Swapchain、Command Buffer、同步原语；
- Descriptor、Pipeline、显存分配、资源状态和帧内资源；
- CPU/GPU 同步、上传队列、Validation Layer 和故障定位；
- 在两个真实后端之间提取最小 RenderDevice，不追求一次性完美抽象。

阶段成果：

- MiniStudio v0.9；
- Vulkan 绘制核心场景，并与 OpenGL/OpenGL ES 结果对照；
- 提交一次跨后端架构取舍记录和迁移复盘。

### 阶段 H：素材引擎与 AI 创作闭环（第 22～24 月 / 第 92～104 周）

核心内容：

- 图片、3D、动画素材的统一描述、版本、依赖、缓存和运行时转换；
- 导入、组合、参数编辑、实时预览、撤销/重做的最小实现；
- AI 任务的提交、轮询/推送、取消、重试、幂等、下载、校验和缓存；
- JSON Schema/版本协商、Tool Calling、错误回传和客户端可观测性；
- Agent 调用渲染工具完成“导入素材—调整材质—生成预览”的受控流程；
- 理解 RAG 的基本用途，只在创作知识检索确有需求时加入最小检索链路。

阶段成果：

- MiniStudio v1.0；
- 一个可录制演示的 AI 素材到客户端场景闭环；
- 完整 README、架构说明、生命周期说明、性能报告、故障复盘和作品视频；
- 开始投递同方向初级/中初级岗位或争取内部转岗、实习和真实协作机会。

### 阶段 K：规模化性能与架构演进（第 31～33 月 / 第 131～143 周）

## 8. 阶段验收规则

每个阶段至少需要以下证据：

1. **运行证据**：可复现的构建命令、测试场景和输出；
2. **理解证据**：能够解释所有权、线程、CPU/GPU 数据流和关键取舍；
3. **调试证据**：至少一次主动故障注入及定位过程；
4. **性能证据**：涉及性能的阶段必须保存基线、工具、数据和副作用；
5. **工程证据**：警告、Sanitizer、测试和文档达到该阶段要求；
6. **版本证据**：通过验收的课程提交并合并到稳定 `main`，课程分支保留。
7. **架构证据**：模块职责清楚、依赖单向、主要资源所有权可解释；新增功能没有无边界地堆入 `main.cpp` 或万能类。

如果只能照着代码完成但不能解释，阶段不算完成；如果能够解释但工程不可复现，也不算完成。

## 10. 暂缓内容

在主线需要之前，暂缓以下内容：

- 同时深入 DirectX、Metal、Vulkan、WebGPU；
- 自研完整 ECS、通用游戏引擎、物理引擎或 UI 框架；
- 一开始手写无锁队列、自定义分配器或复杂弱内存序；
- 光线追踪、全局光照、NeRF、3DGS、可微渲染等独立大方向；
- 为使用框架而使用 LangChain/LangGraph/RAG；
- 只增加效果数量、却没有资源生命周期、错误处理和性能证据。

这些内容可以在季度复盘时按目标岗位变化加入，但不能同时抢占主线。

## 11. 调整规则

- 连续四周实际投入低于 6 小时：延长当前阶段，不压缩验收。
- 连续四周稳定投入超过 10 小时且验收质量可靠：可以增加一个拓展任务，不跳过基础阶段。
- 获得相关实习、工作或真实项目：优先把课程任务映射到真实需求，并保护公司或客户机密。
- 目标岗位明显转向 Apple：阶段 G/J 可调整为先 Metal、后 Vulkan。
- 目标岗位继续指向 Android/Vulkan 与 AI 创作工具：保持当前优先级。
- 每次季度复盘只调整未来阶段，不改写已经发生的学习记录。
